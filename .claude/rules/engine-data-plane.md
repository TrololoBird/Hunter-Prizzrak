# Вы правите плоскость данных

`engine/` — **единственный транспорт** с 2026-07-19. CCXT только публичный: `fetchOHLCV`,
`fetchOrderBook`, `fetchFundingRate`, `watch_*`. Никогда `createOrder` / `fetchBalance` /
`fetchPositions` / `withdraw` — канон в `docs/ai/rules/prohibited-apis.md`, механически держат
`scripts/check_prohibited_apis.py` (pre-commit) и PreToolUse-хук `guard_edit.py`.

## Четыре ловушки, каждая стоила живого инцидента

**1. Бонд свежести обязан быть ДОСТИЖИМ продюсером.** `FRESH_FUTURES_DATA_S = 360` стоял при
реальном периоде обновления **377.9 с** (замер 2026-07-26: 17 сбросов из 17 за бондом), потому
что период = такт + обход, а обход растёт линейно с юниверсом. Планы позиционирования лежали в
`not_ready` у 57% строк на здоровом прогоне. Правило: бонд считается от ИЗМЕРЕННОГО периода
(`api.py::_poll_positioning`), сон — дедлайнный (`sleep(max(0, POLL_S - walk))`), а не
фиксированный после обхода. Новый бонд обязан нести рядом замер (I-7).

**2. Подписка без списка символов — это подписка на всю биржу.** `watch_bids_asks()` без
аргумента даёт `!bookTicker` всей вселенной: замер 2026-07-26 — 1.4% полезных кадров,
медиана 5.0 с против 0.005 с со списком (×1000). `watch_mark_prices()` без списка парсит
441 символ на кадр при 0.79% полезных — это CPU в том же event loop, что считает
Polars-фичи. **Всегда передавать `list(self._symbols)`.**

⚠ **Причина пяти секунд — троттл БИРЖИ, а не медленный клиент.** Прежняя редакция этого
правила объясняла медиану 5.0 с тем, что «одно сообщение = один символ, а цикл забирает по
одному за итерацию». Это неверно, и вывод отсюда следовал бы ложный — будто помогает читать
быстрее. Binance перевёл `!bookTicker` с real-time на **обновление раз в 5 секунд
2023-12-20**; `<symbol>@bookTicker` остался real-time. Замер 2026-07-31 (32 с): на
`!bookTicker` агрегатный поток — **105.7 кадров/с** по 750 символам, то есть клиент не
узкое место, а медиана интервала **на один символ** — **5.448 с** (BTCUSDT 5.012 с). На
явном списке из трёх символов — 1589 кадров/с и медиана **0.000 с**. Разгребать быстрее
нечего: биржа не шлёт символ чаще. Подробности и источники —
[`docs/engine/exchange-apis-2026-07-31.md`](../../docs/engine/exchange-apis-2026-07-31.md).

⚠ **Но у ликвидаций список работает НАОБОРОТ.** `watch_liquidations_for_symbols([])` с
ПУСТЫМ списком подписывается на `!forceOrder@arr` — один универсальный канал, на котором и
держится трап №3. Передать сюда `list(self._symbols)` (как требует это правило для
остальных подписок) значит получить `<symbol>@forceOrder` **на каждый символ**: универсальность
теряется, `touch_liveness` перестаёт быть законным, а число подписок растёт до размера
вселенной. `ingest.py:394` намеренно передаёт `[]` — **так и оставить**.

**3. Молчание событийного потока — это ДАННЫЕ, а не протухание.** `!forceOrder@arr` шлёт символ,
только если по нему была ликвидация; бонд 60 с превращал «ликвидаций не было» в «фид умер»
(85.7% строк). Различать два времени: `received_ms` — жив ли сокет (по нему считается свежесть),
`event_ms` — когда событие было. Универсальная подписка ⇒ любой кадр доказывает жизнь для всех
символов: `SymbolState.touch_liveness`.

⚠ Но `touch_liveness` **нельзя применять по симптому «план за бондом»** — на `bbo` он
замаскировал бы настоящее отставание в 1000 раз. Сначала измерить, ПОЧЕМУ план отстаёт.

**4. Реконнект без пересева оставляет ДЫРУ в середине кадра.** `Ingest.reconnect` поднимает
подписки заново, но кадры не трогает, а `SymbolState.merge_frame` дописывал хвост по
единственному условию `bar[0] > tail` — без проверки шага. Разрыв дольше пары баров ⇒ новый
хвост приклеивается к старому телу, в середине пустота. Дальше по этому кадру считаются
уровни, накопление и ПОК, при этом `not_ready` чист и штамп свеж: **дыру не видел ни один
прибор**. Сигнатура инцидента `stale-htf-cache-trap`.

Закрыто 2026-08-01 в двух местах: причина — `api.py::Engine._reconnect_and_reseed` (пересев
из REST после подъёма подписок, вместо голого `Ingest.reconnect` у вотчдога); симптом —
`state.py::SymbolState.merge_frame` логирует `kline_frame_gap` с числом пропущенных баров.
Шаг серии берётся из САМОГО кадра (два последних бара), а не из имени плана.

⚠ Бар при обнаружении дыры НЕ выбрасывается: это превратило бы отравленный кадр в
замороженный, что хуже. Дыру чинит пересев, лог — только объявляет её.

## Граница «отказ vs штатная деградация»

Живёт в **одном** месте — `view/build.py::plane_is_required`, рядом со списком запрашиваемых
планов; держит `tests/test_plane_classification.py`. Обязательны только кадры. Копия этого знания
у потребителя — механизм, которым граница уже дважды разъезжалась (детектор блэкаута ослеп на
месяц, потом чуть не устроил цикл перезапусков). Неизвестное имя плана в рантайме **не** отказ:
fail-loud здесь живёт в тесте, потому что в проде он даёт ложный блэкаут.

## Диагностика

`data_plane_audit` и `universe_health` переписаны 2026-07-26 — прежние были слепы. Проверять их
здоровье: `summary.measured_plane_count` (ноль = источник возрастов снова отвалился). Возрасты
берутся ТОЛЬКО из штампов движка (`api.py::plane_ages`), «плана нет» — только из `view.not_ready`.

`/futures/data/*` метрится ОТДЕЛЬНЫМ бюджетом 1000 запросов / 5 мин / IP, вес 0, заголовков
`X-MBX-USED-WEIGHT-*` не отдаёт вообще. ccxt троттлит их против общего ведра и допускает 6.3×
сверх бюджета — единственные настоящие ворота это `rest.py::_FD_GATE`.
