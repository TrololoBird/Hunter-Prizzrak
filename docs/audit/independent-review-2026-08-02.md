## 2. Находки

### F-1. На Windows осиротевший `watch.pid` роняет старт неперехваченным `OSError`, а не перезаписывается
- **Где:** `hunt_core/_cli.py::_acquire_single_instance_lock`
- **Класс:** платформенный дефект (Windows) + расхождение CLAUDE.md с деревом.
- **Доказательство:** на Windows `os.kill(<мёртвый pid>, 0)` даёт
  `OSError(22, 'Параметр задан неверно', None, 87)` — ни `ProcessLookupError`, ни
  `PermissionError`, единственные две ветки, которые ловит код. Замер: три мёртвых/свободных
  pid — все три дали `OSError errno=22 winerror=87`. Затем вызвана **настоящая функция** с
  `paths.DATA`, перенаправленным в скретчпад, и протухшим pid в файле — итог:
  `UNCAUGHT: OSError(22, ...)`.
- **Воспроизведение:** скрипт из скретчпада (`lock_repro.py`): подложить в `<DATA>/watch.pid`
  pid завершившегося процесса, вызвать `_acquire_single_instance_lock()`.
- **Последствие:** после любого некорректного завершения `watch` (BSOD, kill, перезагрузка)
  повторный запуск без `--once` падает трейсбеком до входа в цикл. Бот не рестартует, пока
  человек не удалит файл руками. `HUNT_SUPERVISED_CHILD`-ветка падает так же (исключение
  раньше её проверки).
- **Масштаб:** 100% стартов с осиротевшим замком на Windows.
- **Статус:** ПОДТВЕРЖДЕНО ЗАМЕРОМ.
- **Опровержение:** проверил, не убивает ли `os.kill(pid,0)` живой процесс (нет — жив спустя
  1 с) и не ловится ли OSError выше по стеку (`main()` не ловит). CLAUDE.md-утверждение
  «проверено вызовом функции 2026-07-26» видимо делалось на macOS.

### F-3. Вотчдог тишины фида — одноразовый: свой же реконнект его ослепляет
- **Где:** `hunt_core/engine/ingest.py::Ingest.reconnect` (`last_frame_ms.clear()`),
  `hunt_core/engine/health.py::Watchdog.run` + `feed_silence_s`.
- **Класс:** молчаливая деградация (I-6) + докстринг-ложь.
- **Доказательство:** `feed_silence_s({}, now)` → `None` (исполнено на реальном коде);
  в `Watchdog.run` при `None` метрика пишется как `0.0` («идеально свежо») и ветка
  реконнекта не срабатывает (`silence is not None and silence > bound` → False).
  `reconnect()` делает `self.last_frame_ms.clear()` — после реконнекта, если новое
  соединение тоже молчит (ровно сценарий, ради которого вотчдог существует: бан, DNS,
  мёртвая сеть), словарь пуст навсегда → тишина `None` навсегда → ни повторного реконнекта,
  ни роста `hunter_engine_feed_silence_seconds`. Докстринг `reconnect` утверждает
  «``last_frame_ms`` dict identity is preserved so the watchdog keeps observing» —
  identity да, содержимое нет.
- **Воспроизведение:** `uv run python -c "from hunt_core.engine.health import feed_silence_s; print(feed_silence_s({}, 10**12))"`.
- **Последствие:** тотальный блэкаут, переживший один реконнект, становится невидимым: гейдж
  0.0, лог молчит, `watch` крутится на замороженных кадрах до бондов свежести планов.
- **Масштаб:** каждый реконнект открывает окно слепоты до первого кадра; при мёртвой сети —
  навсегда.
- **Статус:** механизм ПОДТВЕРЖДЁН ЗАМЕРОМ (ветвление исполнено на реальном коде); полный
  сценарий «мёртвый реконнект» на живой сети не воспроизводился — ГИПОТЕЗА только в части
  того, что нет другого страхующего пути (плановый ротейт `WS_ROTATE_S` сработает, но лишь
  раз в сутки и с тем же clear()).
- **Опровержение:** искал второй сторож — `WS_ROTATE_S`-ротейт есть, но период сутки и он не
  зависит от тишины; бонды свежести планов (`view.not_ready`) в итоге закричат на уровне
  тика — но метрика тишины при этом будет лгать «0.0», что прямо запрещено директивой I-6.
