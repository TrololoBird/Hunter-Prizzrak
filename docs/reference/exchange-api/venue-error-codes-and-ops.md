# Вторичные площадки: коды ошибок и операционная семантика (OKX / Bybit / Bitget / CoinGecko)

> **Статус: СПРАВОЧНИК** (собрано 2026-07-31 из ОНЛАЙН-документации).
> Только ПУБЛИЧНЫЕ эндпойнты — ни одного, требующего ключа, подписи или аккаунта.

Что здесь: всё, что нужно, чтобы гонять OKX / Bybit / Bitget / CoinGecko **без тихой деградации** —
коды ошибок публичных market-data поверхностей, keepalive/reconnect (у всех троих он РАЗНЫЙ, и
ошибка выглядит ровно как мёртвый фид), ловушки времени/точности, лимиты подписок.

Чего здесь нет и не будет: коды ордеров, балансов, позиций, плеча, вводов/выводов, суб-аккаунтов,
listenKey/user-data-stream. Такие коды помечены **➖ ИСКЛЮЧЕНО (нужен ключ)** одной строкой и не
раскрываются. Публичная, но «околоторговая» рыночная статистика (ликвидации, OI, фандинг,
long/short, IV) — В ОБЛАСТИ.

**Легенда:** ✅ ИСПОЛЬЗУЕТСЯ + call site · ⬜ НЕ ПОДКЛЮЧЕНО + что даёт · ➖ не нужно + почему.

**Главный вывод по проекту сразу:** ни один venue-специфичный числовой код в `hunt_core` не
читается. Различение идёт **только** по типизированным исключениям ccxt
(`hunt_core/errors.py::classify_runtime_error`, `hunt_core/market/network.py::ws_transport_fatal`,
`hunt_core/engine/ingest.py`), и это осознанно — таблицы ниже нужны, чтобы понимать, ВО ЧТО ccxt
превращает код площадки, и где его отображение неточно.

⚠ **И оба классификатора охватывают МЕНЬШЕ, чем обещает их имя** (сверено по графу вызовов
2026-07-31, а не по названию): `classify_runtime_error` зовётся ровно из одного места —
`errors.py::build_runtime_error_payload` (поле `error_class` телеметрии); `ws_transport_fatal` —
тоже из одного, `runtime/cycle/_cycle_loop.py::run_loop` (asyncio-обработчик исключений, решает
**громкость лога**, а не судьбу символа). Ни один из них не гейт допуска и не признак «символ
мёртв». Это важно для чтения таблиц: строка «ccxt мапит не в тот класс» означает «поедет
диагностика», а не «поедут данные».

## 0. Как площадка попадает в проект

`hunt_core/engine/exchanges.py::make_secondary` создаёт по одному ccxt.pro-клиенту на площадку;
`SECONDARY_VENUES = ("okx", "bybit", "bitget")`. Потребители:

| Что | Где | Транспорт |
|---|---|---|
| фандинг / OI / long-short | `engine/multi.py::MultiEngine._cross_loop` | REST-поллинг, `CROSS_FUNDING_POLL_S` |
| кросс-венью стакан | `engine/multi.py::MultiEngine.cross_orderbook` | REST `fetch_order_book` |
| ликвидации | `engine/multi.py` (класс-докстрока) | WS-only, REST не опрашивается |
| dominance / marketcap (CoinGecko) | `prizrak/dominance_source.py`, `prizrak/marketcap_source.py` | голый aiohttp, **не ccxt**, по умолчанию ВЫКЛ |

Важно для чтения таблиц ниже: **WS-путь у вторичек в проекте почти не задействован** (ликвидации),
основная нагрузка — REST. Но keepalive-раздел всё равно критичен: ccxt.pro поднимает WS-клиент при
первом `watch_*`, и неверный keepalive проявится не ошибкой, а тишиной.

## 1. OKX

### 1.1 Конверт ответа

**REST:** `{"code": "0", "msg": "", "data": [...]}`. Успех — строка `"0"`, не число, не HTTP-200
(HTTP может быть 200 при `code != "0"`).

**Пер-элементный конверт** `sCode` / `sMsg` живёт ВНУТРИ `data[]` для батч-операций: внешний
`code` может быть `"0"` («запрос принят»), а конкретный элемент — с ошибкой в `sCode`. Практически
у OKX это батч-ордера — ➖ ИСКЛЮЧЕНО (нужен ключ), но знать про двухуровневый конверт нужно: если
когда-нибудь появится публичный батч, читать `code` в одиночку будет ложью.

**WS:** `{"event": "error", "code": "60012", "msg": "...", "connId": "..."}`. Плюс `event:
"subscribe"` / `"unsubscribe"` на успех и `arg` с описанием канала.

### 1.2 Коды, релевантные публичным данным

| Код | Официальное сообщение | ccxt → | Транспорт или данные? | Что ОБЯЗАН сделать клиент |
|---|---|---|---|---|
| `0` | — | — | успех | — |
| **50011** | Rate limit reached. Please refer to API documentation and throttle requests accordingly | `RateLimitExceeded` | **транспорт** | Длинный бэк-офф, НЕ короткий ретрай. Реконнект не нужен (REST). Данные НЕ отсутствуют — считать `not_ready`, не нулём. ⬜ |
| **50001** | Service temporarily unavailable / matching engine upgrading, please try again later | `OnMaintenance` | **транспорт** (обслуживание) | Бэк-офф минутами, не секундами. Площадка вернётся; помечать `not_ready`. ⬜ |
| **50004** | Endpoint request timeout | `RequestTimeout` | **транспорт** | Ретрай с джиттером. ⚠ Формулировка OKX «does not indicate success or failure» — про ордера; для публичного GET безопасно повторить. ⬜ |
| **50013** | System is busy, please try again later | `ExchangeNotAvailable` | **транспорт** | Бэк-офф. Отличается от 50011 тем, что это не твоя вина — троттлинг не поможет, помогает только пауза. ⬜ |
| **50026** | System error, please try again later | `ExchangeNotAvailable` | **транспорт** | То же, что 50013. ⬜ |
| **51001** | Instrument ID does not exist | `BadSymbol` | **ДАННЫЕ** | НЕ ретраить никогда. Символа на площадке нет — вычеркнуть из кросс-опроса. Ретрай здесь = вечный шум в логе. ⬜ |
| **60012** | Invalid request (WS) | — | **клиентский баг** | Реконнект НЕ поможет: неверный формат кадра подписки. Чинить код, а не соединение. ⬜ |
| **60018** | Wrong URL or `{param}` doesn't exist (WS) | — | **клиентский баг / данные** | Сначала проверить имя канала и `instId`; только потом подозревать соединение. ⬜ |
| `channel-conn-count-error` | превышено число соединений на канал | — | **транспорт** | Последнее подписавшееся соединение отклоняется. Закрывать лишние, не переподключаться в цикле. ⬜ |
| 60006 / 60007 / 60009 | login timestamp / login failed | — | — | ➖ ИСКЛЮЧЕНО (нужен ключ) — публичным каналам login не нужен. |
| 50013x / 5011x (подпись, ключ) | — | — | — | ➖ ИСКЛЮЧЕНО (нужен ключ). |

⚠ **Ловушка отображения ccxt.** `50001` у OKX официально «Service temporarily unavailable» —
установленная ccxt 4.5.68 комментирует его как «Matching engine upgrading». Смысл для нас один
(транспорт, бэк-офф), но если писать код по комментарию ccxt, легко решить, что это ТОРГОВАЯ
ошибка и её можно игнорировать в market-data пути. Нельзя: она гасит и публичные эндпойнты.

**HTTP-уровень:** при превышении лимита OKX может вернуть `429` вместо `50011`. Обработчик обязан
покрывать оба — ccxt поднимает `RateLimitExceeded` в обоих случаях, и именно поэтому проект,
ловящий тип, а не код, здесь корректен.

### 1.3 KEEPALIVE + RECONNECT

| Параметр | Значение | Источник |
|---|---|---|
| Публичный URL | `wss://ws.okx.com:8443/ws/v5/public` | OKX WS Overview |
| Бизнес-канал (свечи!) | `wss://ws.okx.com:8443/ws/v5/business` | ccxt `pro/okx.py::get_url` — канал с `candle` уходит СЮДА |
| Пинг | **литеральный текстовый кадр `ping`**, ответ `pong` | OKX WS Overview |
| Рекомендация | «Set a timer of N seconds… where N is less than 30» | OKX WS Overview |
| Idle-разрыв | **30 с без данных** → сервер закрывает | OKX WS Overview |

**Что ccxt.pro уже делает (замерено на установленной 4.5.68, не из памяти):**

```
okx    keepAlive= 18000  maxPingPongMisses= 2   precisionMode= 4 (TICK_SIZE)
```

`pro/okx.py::ping` возвращает строку `'ping'`; `handle_message` ловит `message == 'pong'` →
`handle_pong`. Пинг-цикл — `async_support/base/ws/client.py::ping_loop`: спит `keepAlive/1000`,
и если `lastPong + keepAlive * maxPingPongMisses < now`, поднимает `RequestTimeout('… ping-pong
keepalive missing on time')`. Итог для OKX: **пинг каждые 18 с, таймаут на 36 с**.

**Проекту делать НИЧЕГО не нужно.** 18 с < 30 с — бонд достижим с запасом 12 с.

### 1.4 Лимиты подписок

| Лимит | Значение | Что при превышении |
|---|---|---|
| Запросы соединения | 3 в секунду на IP | отказ в соединении |
| `subscribe`/`unsubscribe`/`login` | **480 в час на соединение** | отказ подписки |
| Соединений на канал | 30 на суб-аккаунт | `channel-conn-count-error`, отклоняется ПОСЛЕДНЕЕ |
| Дубли | несколько подписок на один канал в одном соединении считаются за одну | — |

### 1.5 Время и точность

| Что | Значение | Ловушка |
|---|---|---|
| Метки в теле/ответе | Unix **миллисекунды**, СТРОКОЙ (`"1597026383085"`) | строка, не int — сравнение `ts > x` без приведения тихо врёт |
| Метки в заголовках | ISO 8601 UTC мс (`2020-12-08T09:08:57.715Z`) | ➖ нужно только для подписи |
| Свеча `ts` | **время ОТКРЫТИЯ** бара | совпадает с Binance — сдвига нет |
| `precisionMode` | `4` = `TICK_SIZE` (замер) | как у Binance |
| Символ USDT-перпа | `BTC-USDT-SWAP`; ccxt unified `BTC/USDT:USDT` | — |
| **`contractSize`** | **0.01 у `BTC-USDT-SWAP`** (у linear-USDT площадок 1.0) | ⚠ **главная ловушка OKX.** Сырые размеры стакана как base-units завышают глубину OKX в 100×, и самая мелкая книга начинает доминировать в объединённой стене. Задокументированный дефект; лечится в `multi.py::cross_orderbook` (`market_contract_size`, `None` → символ пропускается, никогда `1.0`). ✅ ИСПОЛЬЗУЕТСЯ |

## 2. Bybit (V5)

### 2.1 Конверт ответа

```json
{"retCode": 0, "retMsg": "OK", "result": {...}, "retExtInfo": {}, "time": 1700000000000}
```

`retCode == 0` — успех. HTTP 200 при `retCode != 0` — норма, поэтому проверять HTTP-статус
недостаточно.

### 2.2 Коды

| Код | Сообщение | ccxt → | Транспорт или данные? | Что ОБЯЗАН сделать клиент |
|---|---|---|---|---|
| **0** | OK | — | успех | — |
| **10001** | Request parameter error | `BadRequest` | **клиентский баг / данные** | НЕ ретраить. Обычно неизвестный `symbol` или неверная `category`. Для нас = символа нет → вычеркнуть. ⬜ |
| **10002** | The request time exceeds the time window range | `InvalidNonce` | **ЧАСЫ КЛИЕНТА** | ⚠ Ретрай бесполезен, пока часы не поправлены. Проекту это знакомо: живой замер 2026-07-27 дал сдвиг локальных часов **43.4 с**. Реакция — синхронизация времени и громкий лог, не бэк-офф. ⬜ |
| **10006** | Too many visits. Exceeded the API Rate Limit | `RateLimitExceeded` | **транспорт** | Бэк-офф. Лимит **на эндпойнт**. ⬜ |
| **10016** | Server error / service restarting | `ExchangeError` | **транспорт** | Ретрай с бэк-оффом. ⚠ ccxt мапит в `ExchangeError`, а НЕ в `NetworkError` — значит `hunt_core/market/network.py::ws_transport_fatal` (список `NetworkError/RequestTimeout/ExchangeNotAvailable/ChecksumError`) его **не узнаёт**. Последствие сверено по единственному call site (`runtime/cycle/_cycle_loop.py::run_loop`): рестарт Bybit вылезет **громким orphaned-future трейсбеком** вместо rate-limited debug-строки, а не пометкой «символ мёртв». Шумит диагностика, данные не портятся. ⬜ |
| **10018** | Exceeded the IP Rate Limit | `RateLimitExceeded` | **транспорт, IP-уровень** | Длинный бэк-офф ПО ВСЕМУ КЛИЕНТУ, не по символу. Отличие от 10006: тот на эндпойнт, этот на IP — снижать частоту нужно глобально. ⬜ |
| **10429** | System level frequency protection | `RateLimitExceeded` | **транспорт** | Ретрай после паузы. Соответствует HTTP 429. ⬜ |
| **HTTP 403** | Forbidden request | — | **транспорт / география** | ⚠ Три РАЗНЫЕ причины под одним статусом: (а) «access too frequent» — IP-лимит/бан; (б) пустое тело у GET; (в) IP из США. Различать по телу ответа. Бэк-офф лечит только (а); (в) не лечится вообще. ⬜ |
| **HTTP 429** | System level frequency protection. Please retry | — | **транспорт** | Ретрай с паузой. ⬜ |
| **20003** (WS) | Too frequent requests under the same session | — | **транспорт** | Разредить подписки в одном соединении. ⬜ |
| **20006** (WS) | `reqId` is duplicated | — | **клиентский баг** | ccxt инкрементит `requestId` сам (`pro/bybit.py::request_id`). ➖ |
| 33004 | api key has expired | — | — | ➖ ИСКЛЮЧЕНО (нужен ключ). |

### 2.3 KEEPALIVE + RECONNECT

| Параметр | Значение | Источник |
|---|---|---|
| Публичный linear (USDT-перпы) | `wss://stream.bybit.com/v5/public/linear` | Bybit WS Connect |
| spot / inverse / option | `.../v5/public/{spot,inverse,option}` | там же |
| Пинг | **JSON** `{"req_id": "100001", "op": "ping"}` | Bybit WS Connect |
| Понг | `{"success": true, "ret_msg": "pong", "conn_id": "...", "op": "ping"}` | там же |
| Рекомендованный интервал | **каждые 20 с** | там же |
| Idle-разрыв | **10 минут** без ping-pong И без данных | там же |

**ccxt.pro (замер на 4.5.68):**

```
bybit  keepAlive= 18000  maxPingPongMisses= 2   precisionMode= 4 (TICK_SIZE)
```

`pro/bybit.py::ping` шлёт `{'req_id': …, 'op': 'ping'}`; `handle_pong` умеет ТРИ формы понга
(contract `ret_msg == 'pong'`, spot `{"pong": 1653296711335}`, и `op: 'pong'`) — это не
избыточность, у Bybit они реально разные по типам рынка.

**Проекту делать НИЧЕГО не нужно.** 18 с < рекомендованных 20 с, и на порядок меньше 10-минутного
idle-разрыва. Bybit — самая прощающая из трёх площадок по keepalive.

### 2.4 Лимиты подписок

| Лимит | Значение | Что при превышении |
|---|---|---|
| args на один `subscribe` (spot) | ≤ 10 | ошибка подписки |
| args на соединение (option) | ≤ 2000 | ошибка подписки |
| Длина массива args (все публичные) | ≤ **21 000 символов** | ошибка подписки |
| Новые соединения | **не более 500 за 5 минут** на домен | Bybit прямо не рекомендует частый connect/disconnect; практически — 403 |
| Топиков на соединение | явного потолка нет, кроме двух выше | — |

**Публичные REST-лимиты считаются по IP.** Точный потолок публичных market-data эндпойнтов живёт
на отдельной странице `bybit-exchange.github.io/docs/v5/rate-limit` — **в этом заходе она не
выгружена**, поэтому числа здесь НЕ приводятся. Не подставлять «разумное значение» (I-7): сверить
на странице перед тем, как ставить константу.

### 2.5 Время и точность

| Что | Значение | Ловушка |
|---|---|---|
| `time` в конверте | Unix **миллисекунды** | — |
| Свеча | `start` = **открытие**, `end` = закрытие; оба присутствуют | ⚠ у Bybit в кадре ЕСТЬ оба — взять `end` вместо `start` сдвигает бар на весь таймфрейм молча |
| `confirm` в WS-свече | `true` = бар ЗАКРЫТ | ⚠ прямой инструмент против I-5 (lookahead): форминг-бар помечен явно, отбрасывать по `confirm == false` |
| `precisionMode` | `4` = `TICK_SIZE` (замер) | — |
| Символ USDT-перпа | id `BTCUSDT` + `category=linear`; unified `BTC/USDT:USDT` | ⚠ id совпадает со спотовым — без `category` попадёшь на спот |
| Таймфреймы | `1,3,5,15,30,60,120,240,360,720,D,W,M` (минуты числом!) | `'1h'` → `'60'`, не `'1h'` |

⚠ **`fetchMarkets: {"types": ["linear"]}` в `make_secondary` — не оптимизация, а лечение отказа.**
ccxt грузит четыре категории (spot/linear/inverse/option) и обходит шесть опционных цепочек
отдельными запросами; именно они валили `load_markets` на живом прогоне 2026-07-26 (04:41 и
04:48). Замер A/B: как есть — FAIL за 11.6 с; только linear — OK за 2.8 с и 656 USDT-перпов.
✅ ИСПОЛЬЗУЕТСЯ (`engine/exchanges.py::make_secondary`).

## 3. Bitget

⚠ **Оговорка об источнике.** Документация Bitget (`bitget.com/api-doc/*`) — SPA: прямая выгрузка
страницы отдаёт оболочку раздела «Unified Trading Account», а не содержимое. Три попытки WebFetch
на `websocket-intro`, `contract/websocket/WebSocket-Introduction` и `spot/error-code/websocket`
вернули один и тот же нерелевантный текст. Числа ниже взяты из поисковой выдачи по ТЕМ ЖЕ
страницам плюс из установленного исходника ccxt. **Это слабее прямой выгрузки — перед тем как
превращать любое число отсюда в константу, открыть страницу в браузере.** Помечено ⚠SPA.

### 3.1 Конверт ответа

**REST:** `{"code": "00000", "msg": "success", "requestTime": 1700000000000, "data": {...}}`.
⚠ Успех — строка **`"00000"`**, а не `"0"` и не `0`. Проверка `code == "0"` (по аналогии с OKX)
здесь тихо провалит каждый успешный ответ.

**WS:** ошибка — `{"event": "error", "code": 30001, "msg": "..."}`; данные —
`{"action": "snapshot" | "update", "arg": {...}, "data": [...], "ts": ...}`.
⚠ `action` различает ПОЛНЫЙ снимок и дельту: обработать `update` как `snapshot` — значит
подменить книгу дельтой.

### 3.2 Коды

Таблица ниже — **из установленного `ccxt/pro/bitget.py` (4.5.68)**, то есть ровно то, что
реально поднимется в проекте:

| Код (WS) | Комментарий ccxt | ccxt → | Транспорт или данные? | Реакция |
|---|---|---|---|---|
| **30001** | `instType:sp,channel:candleNone,instId:BTCUSDT doesn't exist` | `BadRequest` | **ДАННЫЕ / клиентский баг** | Канала или инструмента нет. НЕ ретраить. ⬜ |
| **30003** | invalid op | `BadRequest` | клиентский баг | Чинить кадр. ⬜ |
| **30006** | too many requests | `RateLimitExceeded` | **транспорт** | Бэк-офф, соединение живо. ⬜ |
| **30007** | request over limit, connection close | `RateLimitExceeded` | **транспорт + РАЗРЫВ** | ⚠ Отличие от 30006: сервер ЗАКРЫВАЕТ соединение. Нужен и бэк-офф, И реконнект с ре-подпиской. ⬜ |
| **30014** | Request timestamp expired | `BadRequest` | **часы клиента** | Синхронизация времени. ⬜ |
| **30016** | Param error | `BadRequest` | клиентский баг | ⬜ |
| 30002/30004/30005/30011/30012/30013/30015 | illegal request / requires login / login failed / invalid ACCESS_KEY / PASSPHRASE / TIMESTAMP / sign | — | — | ➖ ИСКЛЮЧЕНО (нужен ключ) — на публичных каналах не встречаются. |
| **HTTP/REST `429`** | Too many requests | `DDoSProtection` | **транспорт** | Длинный бэк-офф (`hunt_core/engine/params.py`: короткий ретрай продлевает бан). ⬜ |

⚠ **Конфликт нумерации, который нельзя разрешать угадыванием.** Легаси-документация Bitget
(`bitgetlimited.github.io`, v1, выведенная из OKX) даёт `30006 = invalid ACCESS_KEY` и
`30007 = invalid Content_Type`. Установленная ccxt для v2 даёт `30006 = too many requests` и
`30007 = request over limit`. **Значения РАЗНЫЕ у одного числа.** Практический вывод: на v2-эндпойнте
(`wss://ws.bitget.com/v2/ws/public`, который ccxt и использует) верна трактовка ccxt; но код,
различающий Bitget по ЧИСЛУ, сломается при переходе площадки на v3/UTA. Ещё один довод в пользу
того, что проект ловит типы ccxt, а не числа.

### 3.3 KEEPALIVE + RECONNECT

| Параметр | Значение | Источник |
|---|---|---|
| Публичный URL (v2) | `wss://ws.bitget.com/v2/ws/public` | ccxt `pro/bitget.py` (замер) |
| Публичный URL (v3 / UTA) | `wss://ws.bitget.com/v3/ws/public` | там же; ccxt берёт его только при `uta=True` |
| Пинг | **литеральная строка `ping`**, ответ `pong` | ⚠SPA Bitget WS intro |
| Рекомендованный интервал | **каждые 30 с** | ⚠SPA |
| Разрыв сервером | если **2 минуты** не приходил `ping` | ⚠SPA |
| Нет `pong` | **переподключаться** (прямая рекомендация Bitget) | ⚠SPA |
| Сообщений на соединение | ≤ **10 в секунду**, иначе разрыв | ⚠SPA |

**ccxt.pro (замер на 4.5.68):**

```
bitget keepAlive= 30000  maxPingPongMisses= 2   precisionMode= 4 (TICK_SIZE)
```

`pro/bitget.py::ping` возвращает `'ping'`; `handle_message` ловит и `content == 'pong'`, и
`message == 'pong'`. Итог: **пинг каждые 30 с ровно по рекомендации, таймаут на 60 с** — вдвое
раньше, чем сервер сам разорвёт на 120 с. То есть ccxt заметит проблему первым, это правильный
порядок.

**Проекту делать НИЧЕГО не нужно.**

## 4. CoinGecko

Единственная не-биржевая и не-ccxt поверхность. Используется для доминации/капитализации в
призраке; **по умолчанию выключена** (`PrizrakConfig.dominance_enabled`).

### 4.1 Коды

| Код | Смысл | Транспорт или данные? | Реакция |
|---|---|---|---|
| **429** | Rate limit exceeded — «Reduce call frequency or upgrade your plan» | **транспорт** | Бэк-офф. ⚠ `Retry-After` документацией **НЕ обещан** — интервал выбирает клиент сам. ✅ путь существует, но см. 4.3 |
| **401** | Unauthorized — ключ отсутствует/неверен | конфигурация | ➖ публичный `/global` ключа не требует |
| **403** | Forbidden — доступ заблокирован сервером | **транспорт** | Не лечится ретраем; смотреть на IP/регион. ⬜ |
| **1020** | Access Denied — блокировка CDN-фаерволом (Cloudflare) | **транспорт** | Не ретраить в цикле — усугубляет. ⬜ |
| **10002** | Missing API Key | конфигурация | ➖ нужен ключ (Pro) |
| **10005** | Endpoint not available on your plan | **данные** | Эндпойнт недоступен навсегда на этом тарифе — не ретраить. ⬜ |

**Ключевое правило CoinGecko, которого нет у бирж:** *«All requests count toward your per-minute
rate limit — including 4xx and 5xx errors»*. То есть **ретрай на 429 сам расходует бюджет** и
ретрай-шторм самоподдерживается. Бэк-офф обязан быть экспоненциальным, а не фиксированным.

| Хост | Назначение |
|---|---|
| `api.coingecko.com` | публичный / Demo — ✅ ИСПОЛЬЗУЕТСЯ (`prizrak/dominance_source.py::_COINGECKO_GLOBAL`, `_COINGECKO_MARKETS`) |
| `pro-api.coingecko.com` | Pro | ➖ нужен ключ |

Потолок публичного/Demo-тарифа на выгруженной странице указан как **100 вызовов/мин**; помесячный
лимит зависит от тарифа и там не раскрыт. Проект ходит раз в час (`HUNT_DOMINANCE_TTL_S=3600`) и
раз в 6 ч (marketcap) — запас несколько порядков, вопрос лимита практически не стоит.

### 4.2 Что даёт (не подключено)

⬜ `/coins/markets` с `price_change_percentage` за несколько окон · ⬜ `/global/decentralized_finance_defi`
(DeFi-доминация) · ⬜ `/exchanges/{id}/volume_chart` · ⬜ `/coins/{id}/market_chart` (исторический
ряд капитализации вместо самодельного роллинг-кэша) · ⬜ `/search/trending`.

### 4.3 ⚠ Замечание по I-6 (fail-loud), найденное при сверке

`prizrak/dominance_source.py` документирует **silent-fail** осознанно («any network/parse error is
swallowed; the factor then reads neutral (multiplier 1.0)»), и это законное исключение: источник
вне критического тика, а холодный старт честно отдаёт `None`.

Но конкретно **429 неотличим от «данных нет»**: при устойчивом rate-limit фактор навсегда читает
нейтральную `1.0`, и в логе нет НИЧЕГО. Это ровно тот класс, который проект ловит как «поле,
которое перестало пополняться». Минимальное лечение — не менять поведение, а различить статус:
логировать `coingecko_rate_limited` отдельно от прочих ошибок, чтобы «нейтрально, потому что нет
данных» отличалось от «нейтрально, потому что нас забанили». ⬜ НЕ ПОДКЛЮЧЕНО.

## 5. Сверка `make_secondary`: почему НЕ передавать Binance-тюнинг — правильно

`engine/exchanges.py::make_secondary` намеренно НЕ передаёт вторичкам блок `streaming`
(`WS_KEEPALIVE_MS = 180_000`, `WS_MAX_PING_PONG_MISSES = 3`) и `watchOrderBook: {checksum: True}`.
Замер установленной ccxt 4.5.68 (`ex.streaming` без сети):

| Площадка | ccxt `keepAlive` | ccxt таймаут (`keepAlive × misses`) | Требование площадки | Вердикт |
|---|---|---|---|---|
| binance | 180 000 мс | 360 000 мс (в проекте ×3 = 540 000) | серверный ping-frame | ок, это и есть тюнинг проекта |
| okx | **18 000 мс** | 36 000 мс | пинг < 30 с, разрыв на 30 с idle | ✅ запас 12 с |
| bybit | **18 000 мс** | 36 000 мс | пинг 20 с, разрыв на 600 с idle | ✅ запас огромный |
| bitget | **30 000 мс** | 60 000 мс | пинг 30 с, разрыв если 120 с без ping | ✅ ровно по рекомендации |

**Что было бы, если бы `WS_KEEPALIVE_MS = 180_000` уехал на вторички — по числам:**

* **OKX:** первый клиентский `ping` — на 180-й секунде, сервер закрывает на 30-й секунде без
  данных. На ЖИВОМ канале (bookTicker мажора) соединение выживет за счёт потока данных; умрёт оно
  на ТИХОМ канале — например на ликвидациях, где событий может не быть часами. При этом ccxt-шный
  `RequestTimeout` не сработает до 540 с. Симптом: фид «умирает» именно там, где отсутствие
  событий — это ДАННЫЕ, а не поломка. Проекту этот класс знаком дословно (`!forceOrder@arr`,
  `SymbolState.touch_liveness`).
* **Bitget:** сервер разрывает, если 120 с не приходил `ping`. 180 с > 120 с → разрыв
  **гарантированно каждые 2 минуты, независимо от потока данных.** Самый жёсткий случай.
* **Bybit:** 180 с < 600 с idle → выжил бы. Единственный из трёх.

Итого: решение `make_secondary` корректно, и корректно оно по РАЗНЫМ причинам на разных площадках —
на Bybit оно безразлично, на OKX спасает от тихой смерти тихих каналов, на Bitget от гарантированного
разрыва. Комментарий в докстроке (`OKX/Bybit 18000, Bitget 30000`) сверен замером и **точен**.

`watchOrderBook: {checksum: True}` тоже верно не передан: у OKX своя конфигурация глубины
(`depth:'books'`), а чексумма реализована по-своему на каждой площадке.

## Что не подключено

Полный список ⬜ из документа, по убыванию ценности:

1. **Различение rate-limit по УРОВНЮ на Bybit** (10006 = эндпойнт vs 10018 = IP). Сегодня оба
   приходят как `RateLimitExceeded` и лечатся одинаково; правильная реакция разная — на 10006
   достаточно разредить один эндпойнт, на 10018 нужно снижать общий темп клиента. Даёт:
   перестать глушить весь кросс-опрос из-за одного жадного эндпойнта.
2. **Bybit `retCode 10016` не узнаётся классификатором транспорта.** ccxt мапит его в
   `ExchangeError`, а `hunt_core/market/network.py::ws_transport_fatal` перечисляет
   `NetworkError/RequestTimeout/ExchangeNotAvailable/ChecksumError`. Серверная ошибка Bybit
   («service restarting») пройдёт мимо. ⚠ **Цена ошибки МЕНЬШЕ, чем кажется по имени функции:**
   единственный её потребитель — asyncio-обработчик в `runtime/cycle/_cycle_loop.py::run_loop`,
   который решает только, писать ли трейсбек громко или в rate-limited debug. Даёт: снять шум
   в логе во время рестарта Bybit. **Не** даёт и не чинит «символ помечен мёртвым» — такого
   эффекта у этой функции нет.
3. **Bitget `30007` (`request over limit, connection close`) не отличается от `30006`.** Первый
   требует РЕКОННЕКТА и ре-подписки, второй — только паузы. Даёт: не сидеть на закрытом сокете,
   считая, что просто нет событий.
4. **CoinGecko 429 не логируется отдельно** (см. §4.3) — «нейтрально, потому что забанили»
   неотличимо от «нейтрально, потому что нет данных».
5. **OKX `channel-conn-count-error`** — отклоняется ПОСЛЕДНЕЕ подписавшееся соединение; без
   обработки выглядит как «часть каналов просто не приходит».
6. **Bybit `confirm` в WS-свече** — прямой флаг закрытого бара против I-5; у вторичек WS-свечи
   не читаются вообще.
7. **Bybit точные публичные REST-лимиты** — страница `v5/rate-limit` в этом заходе не выгружена;
   число НЕ подставлено намеренно (I-7).
8. **Bitget UTA v3 WS** (`wss://ws.bitget.com/v3/ws/public`) — ccxt берёт его только при
   `uta=True`; нумерация ошибок там может отличаться от v2 (см. §3.2).
9. **CoinGecko `/coins/{id}/market_chart`** — исторический ряд капитализации вместо самодельного
   роллинг-кэша снимков в `data/dominance_cache.json`, который до 24 ч честно отдаёт `None`.

**➖ ИСКЛЮЧЕНО (нужен ключ), перечислено один раз:** OKX 60006/60007/60009 и вся 5011x-серия
подписи; Bybit 33004 и семейство api-key/permission; Bitget 30002/30004/30005/30011/30012/30013/30015;
CoinGecko 401/10002 (Pro-ключ). Ордера, балансы, позиции, плечо, маржа, ввод/вывод, суб-аккаунты,
user-data-stream — вне области целиком.
